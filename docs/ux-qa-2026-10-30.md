# 사용자 관점 통합 QA

검증 기준은 2026-10-30의 Figma Make 기준 화면 36개, 실제 앱 라우팅, QR 구매 웹, Supabase 운영 데이터와 Commerce Edge Function이다. 정적 화면 존재 여부가 아니라 `입력 → 저장 → 재접속 → 다음 단계`가 이어지는지를 기준으로 확인했다.

## 2026-10-31 재검증

- Chrome 자동 순회로 360×800, 390×844, QR 웹 1440×960을 다시 확인했다.
- 추가로 320×700 소형 화면에서 역할 선택·양측 가입·계정 관리·매장 온보딩 5단계·사진 첨부·양측 협업 조건·QR 편집/미리보기·수령 완료·정산을 끝까지 순회했다. 가로 넘침, 고정 영역에 가려진 조작부, 40px 미만 조작 영역은 발견되지 않았다.
- 크리에이터·매장 홈을 Figma Make의 `오늘의 큐레이션` 2열 구조로 맞추고, 마이 화면을 프로필·성과·관리 메뉴 구조로 재정렬했다. 기존 서버 협업·정산 데이터는 홈 하단과 성과 카드에 유지했다.
- 앱 로그인, 크리에이터·매장 5개 탭, AI 추천 대화, 프로필·DNA, 프로젝트 3단계, 두 번째 상품 이미지 첨부, 매장 프로필·공간 취향·알림·QR 상품 목록을 실제 클릭했다.
- QR 웹은 상품 상세 → 비회원 연락처 확인 → 주문서 → 카드사 선택 → 동의 → 프로토타입 주문 완료 → 주문 내역 재확인까지 순회했다.
- 모든 점검 화면에서 가로 스크롤과 런타임 오류 문구는 발생하지 않았다. 홈의 `전체 보기`, 칩과 상단 텍스트 조작 영역은 44px 이상으로 확장했다.
- 심사용 데모 계정이 실제 Supabase 세션을 요구하던 프로필·DNA·프로젝트·매장 설정 경로를 로컬 샘플 상태로 분리했다. 실제 계정의 서버 저장 경로는 그대로 유지한다.
- 심사용 QR 상품 3개는 API가 느리거나 브라우저 CORS로 차단되어도 로컬 카탈로그로 먼저 표시하고, API 응답을 받으면 서버 이미지·재고로 갱신한다. 시연 중 네트워크 오류가 빈 화면으로 이어지지 않는다.
- 로그인 화면은 Figma 기준의 좌측 워드마크, `다시 만나 반가워요.`, 로그인 유지, 비밀번호 재설정 구조로 재정렬했다.
- 최신 Android preview APK(`kr.curit.mobile`, 0.1.0)를 로컬 release 빌드하고 Pixel 4 API 33 에뮬레이터에 설치했다. `curit://qr/demo-dessert-plate` 딥링크에서 서버 상품·가격·재고를 조회하고 실제 GitHub Pages QR 구매 웹을 여는 경로까지 확인했다.
- 최종 심사용 APK에는 운영 로그인과 분리된 역할별 `프로토타입 바로 보기`를 노출했다. 크리에이터·매장 운영자 모두 로그인 입력 없이 샘플 흐름에 진입할 수 있고, 실제 계정의 Auth·DB 저장 경로에는 영향을 주지 않는다. 최종 파일의 SHA-256은 `27a7dabeaf38ea8b421d30b733e9a27e265fe6115083754c6e22466ee896dc73`이다.
- 매장 데모의 공간 사진을 기본 제공해 `기본 정보 → 공간 취향 → 매장 사진 → 전시 구역 → 최종 확인` 5단계를 중단 없이 진행하도록 보완했다. 매장 프로필의 긴 고객층 정보와 주문번호 표시, 주문·현장 수령 화면의 QR 설정 헤더도 실기기에서 재검증했다.
- Android 에뮬레이터에서 `AI 큐레이터 질문 → 추천 근거·후보 → 협업 제안 → 협업 상세`와 `탐색 추천 카드 → 협업 제안 → 협업 상세`를 각각 실제 터치로 확인했다. 새 제안이 기존 진행 중 협업으로 잘못 표시되던 문제도 수정했다.
- 제안 주체에 따라 승인 순서를 분리했다. 매장이 제안하면 `크리에이터 승인 대기`, 크리에이터가 제안하면 자기 승인을 반복하지 않고 `매장 최종 확인`에서 시작한다. 앱 데모와 운영 Supabase RPC에 같은 규칙을 적용했다.
- Android 심사용 데모의 채팅 목록에 역할별 받은 제안을 제공했다. 크리에이터는 `조건 승인`, 매장은 `매장 최종 확정`을 직접 눌러 다음 상태로 전환할 수 있고, 뒤로 이동한 뒤에도 변경된 상태가 채팅 목록에 유지되는 것을 확인했다.
- 데모 탐색의 크리에이터 커뮤니티에도 샘플 게시물을 제공하고, 소식 작성·팔로우·좋아요·댓글 반응을 서버 없이 시연할 수 있게 했다. 운영 계정에서는 기존 Supabase 저장 경로를 계속 사용한다.
- Android 글자 크기 130%에서 로그인과 QR 상세의 입력·버튼·스크롤을 재확인했고, 150%에서도 핵심 조작부가 잘리거나 가로 스크롤이 생기지 않았다. 150%의 긴 상품 ID는 두 줄로 표시된다.
- APK 최종 매니페스트에서 앱 기능과 무관한 `RECORD_AUDIO`, `SYSTEM_ALERT_WINDOW`, `USE_BIOMETRIC`, `USE_FINGERPRINT` 권한을 제거했다. 알림 수신·FCM·카메라·네트워크와 Android 12 이하 이미지 선택에 필요한 권한은 유지한다.
- 라이브 Commerce 웹훅에 서명 없는 위조 이벤트를 전송했을 때 DB 처리 전에 401로 거부되는 것을 확인했다. 새 QR은 GitHub Pages에서 200을 반환하는 `?qr=상품토큰` 주소를 사용하며, 기존 `/q/상품토큰` 링크도 하위 호환으로 읽는다.

## 남은 한계

- QR 조회 수는 브라우저 익명 식별자를 서버에서 해시하고 상품별 하루 1회만 집계한다. IP·사용자 에이전트는 저장하지 않으며, 실제 계정의 매장 관리·QR 상품 관리 화면에는 서버 집계값만 표시한다.
- Android 앱에는 Firebase 앱 설정과 푸시 토큰 등록 코드가 포함돼 있다. 그러나 EAS 프로젝트에 FCM v1 서비스 계정 자격 증명이 없어 원격 푸시 발송·백그라운드 수신은 아직 검증할 수 없다. preview APK 설치와 딥링크만 확인한 상태다.
- Android 네이티브 Chrome에서 QR 상세 → 비회원 연락처 확인 → 주문서 → 주문자명·필수 동의 → 토스페이 선택 → `55,000원 구매 예약하기` 활성화 → 토스 테스트 결제 iframe 로드까지 확인했다. 유효 결제수단이 필요한 승인 완료는 수행하지 않았으며 서버 재고는 8개로 유지됐다.
- 배포된 Commerce 함수는 `paymentMode:toss`, `webhookReady:true`이다. 다만 `expectedMidReady:false`, `payoutMode:disabled`이므로 운영 MID 고정 검증과 실제 판매대금 지급은 활성화하지 않았다. 출시하지 않는 테스트 시연 범위에서는 의도한 상태다.
- 통신사 본인확인, 운영 상점의 실제 지급은 외부 계약과 운영 심사가 필요한 범위다. 현재는 주문 연락처 확인, 토스 테스트 결제창 진입, 서버 승인 로직·재고·정산 원장 자동 테스트까지 검증한다.
- 마지막 시연 전 실제 iPhone/Android 한 대씩에서 키보드, 홈 인디케이터, 카메라 QR 진입을 수동 확인해야 한다. 브라우저 반응형 모드만으로 기기 안전영역을 완전히 대체할 수 없다.
